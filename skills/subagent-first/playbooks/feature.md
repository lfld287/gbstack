# 功能开发

**硬门禁**　Coordinator 主导设计与验收，按 Review Gate 落实实现与独立审查分离。

1. **追踪受影响的子系统。** 找到现有入口、调用链和消费者，明确新增行为及验收标准。
2. **确定结构。** 跨边界或需要结构定型时，用 [`architect`](../../architect/SKILL.md) 明确模块边界、领域模型和接口。
3. **写齐四项并行检查点。** 不适用项保留原位并写 `n/a: <原因>`，四项不可删除。
   1. **阻塞前置**　列出必须先完成的工作和依赖它的任务。
   2. **独立并行流**　列出可同时推进的工作、owner 与负责文件。
   3. **共享可变状态拆解**　写明共享状态、写入边界与同步责任。
   4. **最小安全拆分**　以可独立验收、无同文件并发写的边界拆分。
4. **实现。** 在 brief 中写清领域模型（状态机、类型模型、表／注册表）与完整文件路径，派 `worker` 拆成可验证的小单元逐个推进。新增行为可用低成本、可重复运行的自动化测试验证时，保留同一测试在实现前失败、实现后通过的证据。改共享原语时同步更新所有消费者并逐一验证。
5. **同表面验收。** 在需求实际使用的运行表面执行验收场景并记录结果。若第 4 步存在低成本、可重复运行的自动化测试，还须核验同一测试在实现前失败、实现后通过的证据。验收结果和适用的测试证据缺一不得通过验收。
6. **收敛争议与审查。** 设计有争议时用 [`interrogate`](../../interrogate/SKILL.md) 收敛，必要时更新实现并复验。高风险或复杂改动按 Review Gate 派独立 `reviewer`。
7. **交付。** 说明建了什么、选了什么及原因，附四项并行检查点和未决决策。

**反模式**　强耦合工作强行并行扇出、跳过审查门禁、连续打断旧 `worker`，导致任务缺少明确的 owner。需要换人时按规程确认原成员停写，再派明确的 owner。
